# B-010: All samples/rwn_decrypted/*.dec files have garbled bodies (stale batch run)
**Status:** FIXED 2026-06-19 — re-ran `scripts/rwn_decrypt.py`; 1145/1146 OK, 1 FAIL (unknown)
**Date:** 2026-06-19
**Keywords:** rwn_decrypted, .dec files, garbled, stale, cipher parameters, P_start, K0, body decryption, batch run, check_dec.py

## Symptom
When parsing .dec files from `samples/rwn_decrypted/`, `h[0]` returns values like `0x6F41ED01` (~1.86 billion) — clearly not a valid dispatch table size. All 1,144 .dec files pass the validation header check (`pt[0:4]==pt[4:8]`) but have garbled bodies. The `check_dec.py` script reports all as "OK" because it only tests the validation header — it does not verify the body bytes.

## Root Cause
All .dec files were generated by an earlier batch run of `scripts/rwn_decrypt.py` that used incorrect cipher parameters for the body decrypt step. Possibly the body P_start was set to P_initial (wrong) instead of K0=Encrypt_K(P_initial) (correct), or the key itself was a prior incorrect value. The validation header uses K0[0:8] to XOR — once K0 was corrected for the header, the batch was re-run for headers only but not re-run end-to-end for bodies.

**Evidence:** `compare_suwin7.py` confirmed: live decrypt of suwin7.rwn from share ≠ suwin7.rwn.dec body bytes. T7MSG.RWN live decrypt gives `h[0]=16` (2 instructions, correct); .dec body gives `h[0]=0x6F41ED01` (garbage).

## Attempts
**Workaround (used throughout Pass 110/110b):** Decrypt directly from the network share (`\\i2s109-solidcrm\DBAMFG$`) using the `decrypt_body()` function in scratchpad scripts. This produces correct results. Reading from share is read-only (allowed by CLAUDE.md §1).

**Fix:** Re-ran `python scripts/rwn_decrypt.py` against the network share to regenerate all .dec files. Wrote correct decrypted bodies to `samples/rwn_decrypted/`. Result: 1145/1146 OK, 1 FAIL (unknown).

## Resolution / Lesson
IMPORTANT: Never trust `samples/rwn_decrypted/*.dec` file bodies until after the re-run. The validation header (first 8 bytes) is reliable; everything after byte 8 in stale files was wrong.

The `check_dec.py` validation check is not sufficient — it only tests the 8-byte validation header, not the decrypted body. Always verify body content (e.g., h[0] should be a small integer for a valid dispatch table) when trusting batch-decrypted files.
